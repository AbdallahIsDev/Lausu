# GPUI overlay prototype

Standalone, throwaway GPUI prototype of the dictation bubble. It is **not** part
of the app build, the Tauri workspace, or any CI workflow. Nothing in
`src-tauri/`, `voice_typer/`, or `voice_typer/client/` is touched by this folder.

What it does: renders the existing bubble states with placeholder data in a GPUI
window, consuming the **existing** sidecar→overlay event names/payloads on stdin
as newline-delimited JSON. It does not reproduce the shipped overlay window
styles (transparent / no-activate / always-on-top / click-through) — those need
raw Win32 work and a real desktop; see `docs/design/gpui-overlay.md`.

## Files

- `Cargo.toml` — standalone crate; `[workspace]` keeps it out of the app workspace.
- `src/protocol.rs` — sidecar→overlay event envelope and overlay→host command names.
- `src/state.rs` — mirror of the shipped bubble mode table and state application.
- `src/view.rs` — GPUI `Render` implementation (placeholder pill).
- `src/main.rs` — stdin/JSONL reader + GPUI window wiring.
- `sample-events.jsonl` — minimal recording→transcribing→hide sequence.

## Windows build requirements (exact, local agent)

GPUI-CE 0.3 requires Rust **1.95+**, the **MSVC** toolchain and the **Windows
SDK** (upstream: <https://crates.io/crates/gpui-ce>, <https://gpui.rs/examples/>).
This repository's dev toolchain is GNU (`stable-x86_64-pc-windows-gnu`) because
the Tauri host uses the GNU plumbing; do **not** change that. Use a separate shell
for this prototype:

```powershell
rustup toolchain install stable-x86_64-pc-windows-msvc
rustup default stable-x86_64-pc-windows-msvc
# Verify in a "Developer PowerShell for VS": cl.exe and link.exe must resolve.
where cl
where link
```

From the repository root:

```powershell
cd tools\overlay-gpui
cargo check --all-targets
cargo test
cargo run -- --demo
```

`--demo` injects a fixed placeholder event sequence so the window opens without
a piped stdin, and prints sample overlay→host command lines (`bubble_resize`,
`bubble_hide_complete`, `bubble_toggle_dictation`) to stdout. For the documented
protocol path:

```powershell
Get-Content .\sample-events.jsonl | cargo run
```

GPUI must run in an interactive desktop session with a working GPU/direct3d
device. It cannot run in a headless sandbox or behind a plain HTTP fetch.

Sandbox note (this machine): a GNU-toolchain `cargo check` also needs
`C:\msys64\mingw64\bin` on `PATH` for `dlltool.exe`, and the build cache needs
several GB. If C: is low on space, set
`$env:CARGO_TARGET_DIR = "D:\overlay-gpui-target"` before `cargo check`. This is
only for checking here; production builds use the MSVC/SDK recipe above.

## Protocol (reuses the shipped vocabulary; no second protocol)

Input: one JSON object per line on stdin, the same envelope the sidecar already
publishes (`{"type": "<event>", "data": {...}}`). Consumed types:

| Event | Payload (`data`) |
| --- | --- |
| `bubble_show` / `bubble_hide` | `{}` |
| `bubble_config` | `bubble_position`, `bubble_behavior`, `bubble_mic_button`, `bubble_show_recording_timer`, … |
| `bubble_set_state` | `{"state": "recording"|"transcribing"|"loading"|"idle"|"error"|…, "message"?, "transcript"?}` |
| `bubble_level` | `{"rms": 0..1, "peak": 0..1}` |

The "hint" pushes `still_transcribing` and `cloud_cancel_requested` keep the
`transcribing` mode, mirroring the shipped reducer.

Output: one JSON object per line on stdout using the **existing** host command
names and argument keys (`bubble_signal_ready`, `bubble_resize` with
`width`/`height`, `bubble_hide_complete`, `bubble_toggle_dictation`). Here JSON
lines replace Tauri `invoke`; that is a transport substitution only, not a new
protocol.

This prototype reads stdin to EOF before opening the window. A production
renderer needs a streaming bridge (named pipe / websocket) that feeds entity
updates on GPUI's foreground executor; that gap is recorded in the design doc.
